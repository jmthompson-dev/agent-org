  2. **Level-choice consistency (report 08 §4):** the same prompt lands on Level 1 in some runs and Level 2 in others, so some jobs skip verification they needed. Fix it so the same job gets the same level, and when the choice is borderline, take the higher level. Validate by running the same prompts repeatedly and checking the level matches every time. Its own inspect/fix/validate phase, after v0.2.1 and before Phase 1 below.
- **Builds on:**

  - the repo key from V21-9

## Requirements

| # | Requirement |
|---|---|
| V1 | Claude gets better over time through context: your corrections, your templates, environment facts and past decisions. Not model changes. |
| V2 | Everything you build up survives plugin updates and upgrades cleanly when formats change. |

## Design

### T. Template library
- **T1. `/agent-org:template` (user-only, D14).**
  - **Input:** two to five reference repos plus the pattern to extract (for example, "the consumer station").
  - **Step 1, a script:** inventories each repo (layout, classes, config keys, logging calls, tests) into a batched JSON summary.
  - **Step 2, the model:** compares the summaries. What all repos share is the pattern; what differs is noise or variation points.
  - **Output:** a draft template.
- **T2. Approval and provenance.**
  - **Approval:** a draft is `status: draft` until you approve it. Shared code can share a bug, so comparison isn't proof.
  - **Provenance:** every template records its source repos and commits, the files used, and its variation points (what a new instance must fill in).
- **T3. Storage:** `~/.agent-org/templates/<name>/`, holding `TEMPLATE.md` (when to use it, structure, variation points, rules), skeleton files, and `SOURCE.json`.
- **T4. Discovery at every level.**
  - **Index:** a SessionStart hook loads a one-line-per-template index, capped and separate from the rule card (report 07 E1: its own 10,000-character budget).
  - **Use:** when a task matches a template, Claude **asks before using it** ("Use template `consumer-station`?") and names the template in its plan or intent.
  - **Real matches only:** it asks on a real match, never speculatively.
- **T5. Staleness.** A script compares each template's source commits with the source repos' current HEAD for the files used, and flags changed templates at session start (one line) and in `/agent-org:template --check`.

### L. Lessons, revived and narrowed
- **L1. Sources, in order of value:**
  - **Your corrections:** "no, we do it this way".
  - **Failed approaches:** what was tried and didn't work.
  - **Environment facts the code doesn't show:** the report 08 TZ case.
  - **No specialist `lessons:` blocks.**
- **L2. Capture.**
  - **Hook:** a `UserPromptSubmit` heuristic spots a likely correction, for example a negation followed by an instruction ("no, use…", "don't…, instead…", "we always…"). It injects one line: "If this corrects your earlier work, offer to save it as a lesson."
  - **Offer:** Claude offers a one-line lesson, and one word from you files it with `/agent-org:remember`, which you can also run directly.
  - **No model screen:** you wrote it, so you reviewed it. The regex secret blocklist still runs, because pasted secrets happen.
- **L3. Storage:** `~/.agent-org/memory/{global,projects/<key>}/` with an `INDEX.md` per scope, plus the M6 note header (topic, applies_when, evidence, status). Loading and search follow the M8/M9 mechanics: a capped index at session start and a search script.
- **L4. Decision records.**
  - **Form:** `/agent-org:remember --decision` saves what was decided, **why**, and what was rejected.
  - **Use:** Claude checks decisions before proposing a change in that area, so it stops reopening settled choices.
  - **Prompt:** when you reject a proposal with a reason, Claude offers to record it.
- **L5. Lessons are leads (M7):** re-verify against the current code before acting.
- **L6. Incidents and bottlenecks.**
  - **Incidents:** when a job reaches VERIFIED after a failed attempt (a FAIL `result`, a claim-check block, or a retry in the audit log), Claude offers a one-line incident record: the problem, root cause and fix, with commit and files as evidence. One word from you files it, same as L2.
  - **Bottlenecks:** a script reads the audit log and flags the same failure, stall or denied approval recurring across jobs in a repo. It proposes a bottleneck record at session start (one line). You approve it or dismiss it.
  - **Use:** the PM checks incidents and bottlenecks for the files and area in an intent, and names any it relies on.
  - **Storage:** same scopes and header as L3, with `type: incident | bottleneck`.

### P. Promotion and scoring (the improvement loop)
- **P1. Usage.** A PostToolUse `Read` hook, filtered by `if` (report 07 E2), counts note and template reads. The search script counts what it prints.
- **P2. Outcome scoring.** When a session that read a lesson ends, record the task outcome from the audit log. "Ends" means a PASS or FAIL `result`, an intent VERIFIED, or a claim-check block. A lesson tied to repeated failures gets flagged for review.
- **P3. Promotion.** A user-only `/agent-org:promote` lists lessons above a use threshold that have clean outcomes, and drafts each as one of:
  - a line for the repo's `CLAUDE.md`
  - a template change
  - a skill draft

  You approve each one. agent-org never writes into a repo or skill folder without that approval.
- **P4. Pruning (V4).** Superseded, flagged and long-unused lessons move to `archive/`. Nothing is deleted automatically.

### S. Skill and script standard (new decision)
- **S1. Prefer scripts wherever the work is mechanical.** Three shapes:
  - **Script:** the work is mechanical.
  - **Hybrid:** `SKILL.md` plus scripts in the same folder. The MD says when to run each script and how to judge the output. **No code in the MD.**
  - **Text-only:** pure judgment, such as architecture review.
- **S2. Batching:** scripts take many items per call (JSON on stdin or a file), never one item per turn.
- **S3. Python, standard library only.**
  - **Version:** minimum version set in Inspect (≥ 3.9 unless Windows says otherwise).
  - **No dependencies:** no third-party packages, no venv.
  - **Paths:** `pathlib` for every path.
  - **Encoding:** UTF-8 explicitly on file I/O.
- **S4. Launcher.** Skills call the script through one documented command that works on macOS and Windows: `python3`, then `python`, then `py -3`. Beware the Windows Store `python3` alias that opens the Store instead of running.
- **S5. No Bash tricks.** Claude Code on Windows runs through Git Bash. Avoid `sed -i`, process substitution and `/dev/stdin` assumptions.
- **S6. Hooks stay Node** (v0.2's existing hooks). One language per skill. Inspect must confirm `node` is on the Windows machine's PATH, because every v0.2 hook depends on it.

### D. Your data: versioned and portable
- **D1. One home for your data:** memory, templates, decisions, audit and intents all live under `~/.agent-org/`, outside the plugin. Plugin updates never touch it.
- **D2. Format version.**
  - **Version file:** `~/.agent-org/VERSION` holds the data format version.
  - **Upgrade:** at SessionStart, if the plugin expects a newer format, it runs the matching migration scripts. Each one backs up first, is idempotent and can be rolled back.
  - **Downgrade:** a plugin older than the data refuses to write and says why.
  - **First migration:** V21-9's repo-key migration.

### A. Audit summary and self-diagnosis
- **A1. New audit fields.** Add the improvement signals the log lacks:
  - level chosen
  - cost and turns, where available
  - corrections offered and accepted
  - templates offered and used
  - denied approvals
  - false-block retractions
  - counts only, no content
- **A2. `/agent-org:stats` (user-only).** A script turns the local audit log into a short summary of counts and rates only: no paths, prompts or code. A coworker can send it to you with no FedEx data leaving their machine. The output format is fixed, so it's safe to share.
- **A3. `/agent-org:diagnose` (user-only).**
  - **Input:** stats from you, or several summaries from coworkers.
  - **Analysis:** finds patterns such as repeated false blocks, the same prompt landing on different levels, and templates declined.
  - **Output:** proposed fixes as a report in the agent-org working tree.
  - **Limit:** it **never edits the plugin, hooks, guard or generator spec.** You approve fixes, and they ship through the normal release. A model editing its own safety rails defeats the rails, and the pinned install would wipe the edits anyway.

### W. Windows before 1.0
- Install and run v0.3 on your Windows work machine before any coworker installs it.
- The checklist gets a Windows section: hooks fire, the guard works, skill scripts run through the launcher, paths resolve, and the audit log writes.

## Out of scope for v0.3
- Specialist-sourced lessons, the detached filer and the Haiku screen (dropped after report 08).
- Building our own tool or skill search. Claude Code already loads only descriptions, and user-only skills load nothing. Inspect measures startup context, and we act only if it's bloated.
- Feature-level delivery (ledger, tests-first, contract freeze): v0.4/v0.5. It builds on V6: a feature spanning weeks needs its decisions, incidents and open issues carried between sessions.

## Phases (each ends "stop and report")
1. **`10-inspect-v0.3.md`** (read-only, plus cost-gated probes):
   - **Windows:** `node` and Python availability and versions; which launcher works; Git Bash behavior; whether v0.2 hooks fire.
   - **Startup context:** the current startup context size.
   - **Correction scan:** a script reads your existing Claude Code transcripts and counts likely corrections, and how often the same one repeats. It reports **counts and categories only, no text**, since transcripts include FedEx work. This sets the threshold for L2's heuristic, and if repeats are rare, it says so.
   - **Template mechanics:** re-verify T and L mechanics against the current Claude Code version.
2. **Generate in slices,** each with unit tests, mirrored in `02-generate.md`:
   1. S (the standard) and D (data versioning)
   2. T (templates)
   3. L (lessons and decisions)
   4. P (promotion and scoring)
   5. A (stats and diagnose)

   Add the new decisions, and bump to 0.3.0.
3. **`11-validate-v0.3.md`** (cost-gated, scratch repos):
   - **Template A/B:** build a new instance of a pattern from reference repos versus from the approved template. Compare cost, turns and review findings. Use a generic fixture in this repo; run your real-repo A/B privately and report numbers only.
   - **Correction loop:** a correction offered, accepted, loaded next session, and the repeat avoided.
   - **Decision records:** a recorded decision stops a re-proposal.
   - **Promotion:** drafts a `CLAUDE.md` line, and nothing is written without approval.
   - **Data:** survives a plugin version bump; a migration runs once and is idempotent.
   - **Stats:** contain no content.
   - **Diagnose:** edits nothing.
   - **Incidents and bottlenecks:** a fail-then-fix job offers an incident record; a seeded recurring failure produces one bottleneck proposal.
   - **Regression:** the v0.2 checks still pass.
4. **Field trial (several weeks, your own repos, memory on).** Single-session runs can't show learning over weeks, so this is the release gate. Track from the audit log, counts only:
   - **Re-asked questions:** the PM asks something a decision record already settles.
   - **Repeat incidents:** the same root cause hit twice.
   - **Contradicted decisions:** work that goes against a recorded decision without naming it.
   - **Turns and cost per job** on the same repo, week over week.
   Pick the repos and the trial length before starting. Stop and report.
5. **Release checklist,** including the Windows section (W). Then tag 0.3.0.

## Success criteria
- The template A/B shows a clear cost or rework gain over pointing at reference repos.
- Repeated corrections measurably drop after capture.
- Over the field trial, re-asked questions, repeat incidents and contradicted decisions trend down week over week.
- Nothing is learned, promoted or applied without your yes.
- Your data survives an upgrade.
- It runs on Windows.
