# agent-org v0.2.0 plan

## Requirements v0.2 must meet

| # | Requirement | v0.1 status |
|---|---|---|
| R1 | Minimum effective agents. Right-sized, not few: one agent for a one-piece job, parallel agents when the job splits. | Met |
| R2 | Little information in, blocking questions back, then the job gets done | Met (single task) |
| R3 | Auditing: a trustworthy record of who did what, and independent review where it's warranted | Partial |
| R4 | Hallucination prevention **at every level, 0–3** | Partial (instruction-only, Level 2+ only) |
| R5 | Agents work in parallel | Partial (independent tasks already run side by side in one tree; no ownership check or collision handling) |

## Design

### A. Hallucination prevention at every level (R4)
The principle: a claim needs evidence, and the check scales with the level. Agents are added only where independence is needed (R1).

| Level | Grounding | Verification | Extra agents |
|---|---|---|---|
| 0 | Claims about code cite `file:line` actually read this session. External facts get a source or are marked unverified. Never invent APIs, flags or config keys; grep or read before naming one. | Claim-evidence hook (A1), including the citation check | none |
| 1 | As Level 0. Read the code before editing. Run the tests after. | A1, plus a required test run if the repo has tests | none |
| 2 | As Level 1, plus the PM grounds the intent in files it actually read | A1 on the main thread **and** on every specialist report (A2). The main thread re-verifies: reruns the tests itself, and checks that the reported changed files match the actual `git diff`. | none beyond the assigned specialists |
| 3 | As Level 2 | Everything above, plus **one** independent auditor agent that reproduces the key claims before VERIFIED | +1 auditor |

**A1. Claim-evidence hook (deterministic, no agent).**
- Runs as a `Stop` hook for the main thread and a `SubagentStop` hook for specialists. It reads the transcript.
- It scans the final message for verification claims, such as "tests pass", "I ran", "build succeeds", "verified", "no errors", or "N/N passed".
- It checks that a matching tool call exists in the turn and actually succeeded.
- If a claim has no evidence, it **blocks the stop once** with a reason ("claim 'tests pass' has no test run in this turn: run it or retract it"). On the second attempt it allows the stop but appends a warning, to avoid loops.
- **Citation check.** It also extracts every file the final message cites (`path` or `path:line`) and checks that the session actually opened it (a `Read`, `Grep` or `Glob` on that path, or an edit to it). A cited file that was never opened blocks the stop once: "you cite config.js but never read it: read it or drop the claim." It catches invented files, not misread lines: it can't check that line 40 says what the answer claims.
- It's fail-open and never logs content.

**A2. Report contract check.** Specialist reports must include outcome, the commands run with their exit status, and changed files. The `SubagentStop` hook flags any report missing those, and any "PASS" with no command evidence.

**A3. Grounding rules.** Add grounding rules to the `SessionStart` rule card, kept short, and to every runtime binding: cite read files, never invent identifiers, and mark anything unverified as such.

### B. Parallel execution (R5) that stays minimal (R1)
- **B1.** The PM marks tasks as parallel **only** when all three hold: they own disjoint files or directories; neither consumes the other's interface (or the interface is pinned in the intent first); and each is big enough to justify a specialist starting cold. The intent assignments table gets an "Owns" column. Otherwise the tasks run sequentially or go to one specialist. Parallelism is decided by independence, not by lane: the same specialist id may be dispatched several times in parallel (e.g. two `full-stack-developer` instances on unrelated features).
- **B2. One shared working tree, no worktrees.** Parallel specialists work in the same checkout, as in v0.1, so there's nothing to merge and no commit or merge step to hit the ask rules. Separation comes from B1's file ownership. Specialists are dispatched **without a name**: while agent teams are enabled, a named `Agent` call launches a teammate (confirm in Phase 5).
- **B3. Collision check after the fact, then re-plan.** Detection, not prevention: no per-agent ownership guard in v0.2.
  - When all parallel reports are in, the main thread attributes each changed file to the agent that changed it (its report plus its `Edit`/`Write` calls) and compares that with the intent's "Owns" column and the actual `git diff`.
  - A **collision** is any file changed by two agents, changed outside an agent's ownership, or changed with no attributable agent.
  - A collision is a re-plan trigger. The main thread stops and tells the user which file and which agents. The PM reruns the affected task **sequentially, on top of the current state**, and the user approves. **No fixer agent:** it would be guessing what two agents meant.
  - Each collision is recorded in the audit log; repeated collisions show the PM is splitting work badly.
  - With no collision, the main thread runs the full verification once on the combined result.
  - Build a per-agent ownership guard only if real runs show agents straying.
- **B4. Agent teams as a fallback, not a default (supersedes D7).** Subagents are the primary execution mode. The PM marks a task group `Mode: team` only when the parts are **coupled in a way the PM can't write down up front**: the hand-off (an interface, contract, constraint or hypothesis) has to be discovered while working. Complexity or size alone never justifies a team.
  - **Justification is mandatory.** A `team` task group must state in the intent which hand-off can't be pinned in advance and why. If the PM can write the hand-off down, it pins it in the intent and uses subagents (sequentially or in parallel per B1).
  - **Typical team cases:** debugging with competing hypotheses, where teammates try to disprove each other; a migration and the code change that must land with it, when data and app constraints shift as work proceeds; security review alongside implementation, when findings change the design mid-flight; performance work, when profiling keeps redirecting the others; an API contract that has to be discovered during the build (a contract that can be agreed up front is **not** a team case).
  - **The user approves the mode** at the same gate as the rest of the intent. The summary shown for approval names the mode and the justification.
  - **Flag handling.** Teams need `CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS=1` and an interactive session. If either is missing, `deliver` says so and offers two options, without picking one: enable the flag, or run the group sequentially with one specialist owning the coupled parts. Subagent dispatches are unnamed so they stay subagents even when the flag is on (B2).
  - **Constraints that come with teams:** only the main thread is the lead; teammates share one working tree, so the "Owns" column is mandatory and the B3 collision check applies to teams too (it needs hooks to identify which teammate changed what: Phase 5 F3); teammates can't nest; teams don't survive `/resume`.
- **B5. Conflicts escalate through re-planning, never directly.** Specialists can't start or request a team themselves. A specialist that hits a conflict with another's work (an interface it can't satisfy, a contradicting change) reports `BLOCKED` and names the hand-off in dispute. The main thread treats that as a re-plan trigger: back to the PM with the conflict, the PM may change the mode to `team`, and the user approves the change at the gate. Each such conflict is recorded in the audit log, since repeated conflicts show the PM misjudged the coupling.

### C. Auditing (R3)
- **C1. A model-independent audit log.** Hooks on `PreToolUse` (Agent) and `SubagentStop` append to `~/.agent-org/audit/<repo>.jsonl`, recording: timestamp, session, intent path, agent id, model, dispatch or result, outcome, exit status of claimed commands, and any A1/A2 flags. Never content.
- **C2. Tamper-evident, not tamper-proof.** The intent file stays the human-readable record; the audit log is the machine record, written by hooks directly, not through tools. The model *can* reach it through Bash, so:
  - **Hash chain:** each line carries a hash of the previous line, so any edit or deletion breaks the chain.
  - **Guard:** `ask` on any tool call that touches `~/.agent-org/audit/`.
  - **Detection and notification:** the `SessionStart` hook verifies the chain every session and, if it's broken, shows a warning at the top of the session naming the file and line. A user-only verify command checks it on demand.
  - Desktop notifications are deferred (per-OS maintenance).
- **C4. Teams are audited too.** The `TaskCreated`, `TaskCompleted` and `TeammateIdle` hooks append team events to the same log (team, teammate, agent type, model, task, outcome, flags; never content). Teammate-to-teammate messages bypass the main thread; log their metadata (sender, recipient, time) if a hook exposes it, and document the gap if none does.
- **C3.** Independent review stays proportional. QA and InfoSec join when triggers fire, and the auditor joins at Level 3. R1 is preserved.

### D. Scope-growth protection (keeps the levels honest mid-task)
- **D1. File counter.** If the main thread (no `agent_type`) edits more than about 3 distinct files in a session with no APPROVED intent for the repo, the guard asks: "This job has grown past Level 1. Approve to continue, or escalate with agent-org:deliver."
- **D2. Risky paths.** A main-thread edit to migrations, CI workflows, IaC/k8s/helm or auth code with no APPROVED intent gets the same ask on the first file.
- **D3.** It always uses `ask`, never `deny` or `allow`, and fails open. State lives in `~/.agent-org/state/`, keyed by `session_id`. Specialists are exempt.
- **D4. Approvals are session-scoped.** An APPROVED intent switches D1/D2 off only for the session in which it was approved, recorded under `~/.agent-org/state/<session_id>`. A new session starts with the guard on until something is approved again, so an old approval can't disable it forever.
- **D5. Bash edits are a documented gap.** `sed -i`, redirects and scripts bypass the tool-based counter, the same gap the QA rule has. Accepted for v0.2; the B3 collision check catches most of it in parallel work.

### E. Out of scope for v0.2
- **Autonomous commits after approval.** That needs a deliberate permission design, since ask rules can't be conditional. Revisit in v0.3.
- **Trimming unused personas.** Revisit with usage data.
- **Scoping QA's Bash.** Revisit only if it's seen in practice.
- **Per-agent ownership guard** (prevention instead of B3's detection). Revisit if runs show agents straying.
- **Desktop notifications** for a broken audit chain. Revisit if the session warning gets missed.

## Phases (each prompt ends "stop and report")
1. **`05-inspect-v0.2.md`:** verify every capability the design depends on, before anything is built.
2. **Update `02-generate.md`,** then regenerate. Add decisions D25–D30 (hallucination at every level, shared-tree parallelism with collision re-planning, tamper-evident audit log, scope-growth guard, Level 3 auditor, agent teams as a justified fallback with conflict re-planning; D30 supersedes D7). Bump the version to 0.2.0.
3. **`06-validate-v0.2.md`** (live, cost-gated, scratch repo), with these acceptance checks:
   - **Level 0:** a question whose answer would tempt the model to invent an API. It cites `file:line` or says it's unverified.
   - **Citation check:** an answer that cites a file never opened this session is blocked once, and the model reads it or drops the claim.
   - **Claim hook:** a Level 1 run where the model claims tests pass without running them. A1 blocks it once, and the model runs or retracts.
   - **Level 2:** a specialist report with a false "PASS". A2 flags it, and the main thread's re-verification catches it.
   - **Right-sizing (R1):** one job with three coupled parts (backend endpoint, a frontend page that consumes it, docs for it), given as a one-line description. Expect blocking questions, approval and **exactly one** `agent-org:full-stack-developer`. More agents here is a failure: the page depends on the endpoint's contract, so splitting it adds merge risk and cold starts for no gain.
   - **Parallel (the headline test, R5):** one job with two independent parts that own disjoint files and share no interface, e.g. two unrelated features in separate modules, given as a one-line description. Expect two `full-stack-developer` instances (or the right specialist for each part, if they differ). Expect blocking questions, approval, both running at the same time in the shared tree, a clean collision check, verification on the combined result, and no agent that wasn't needed.
   - **Collision:** two parallel tasks whose work overlaps on one file. Expect the collision to be detected and named, a re-plan with a sequential rerun after approval, no fixer agent, and the collision in the audit log.
   - **Audit:** the audit log has every dispatch and result, with correct models and outcomes, for that job.
   - **Tamper detection:** edit one line of the audit log; the next session shows the broken-chain warning with file and line, and the verify command reports it.
   - **Scope growth:** a "small" task that sprawls to 4+ files trips D1; a first edit to a migration trips D2; in a new session after an approval, the guard is back on (D4).
   - **Level 3:** exactly one auditor agent, and it reproduces the key claim.
   - **Team fallback (interactive; teammates don't spawn in `-p` runs):** a job whose hand-off genuinely can't be pinned up front (e.g. a bug with two competing hypotheses). Expect `Mode: team` with a stated justification, approval of the mode, teammates spawned from agent-org definitions with strict file ownership, team events in the audit log, and verification by the main thread.
   - **No needless team:** a coupled job whose contract *can* be pinned (endpoint plus the page that consumes it) stays on subagents, with the contract written in the intent. ×2.
   - **Flag off:** with teams disabled, a team-worthy job makes `deliver` state the requirement and offer both options without choosing.
   - **Conflict re-plan:** a specialist that hits a conflict reports BLOCKED; the main thread re-plans through the PM and asks for approval before any team starts; the conflict is in the audit log. No specialist spawns or requests a team directly.
   - **Regression:** the v0.1 checks for blocking questions, roster, Status sequence and guard.
   - **Release checklist:** Phase 6 turns the manual team steps from Phase 5 (F7) into `docs/release-checklist.md` in this repo.
4. **Release v0.2.0.** Before tagging, run `docs/release-checklist.md` by hand and record the result as a report under `reports/`. If the checklist is missing, the release stops: it's never auto-created, because a blank checklist would pass every time. The checklist is for releasing agent-org only; the plugin never writes into application repos.

## Success criteria
v0.2 succeeds if the parallel headline test passes end to end, the right-sizing test uses exactly one developer, teams appear only with a stated reason the hand-off can't be pinned, false verification claims get caught at every level, and the agent count never exceeds what the job needs.
