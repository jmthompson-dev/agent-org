## 1. Summary

- **The machine has almost nothing installed, so there are no real conflicts.** User `settings.json` holds only `theme`. There is no `~/.claude/CLAUDE.md`, and no user agents, commands, rules, hooks, routing or guard system. The only extras are two Anthropic plugins synced from claude.ai (`engineering`, `design`). They provide skills and nothing else: no hooks, no agents, no settings.
- **All 14 personas are present and clean** at `production@89a5424`. Each is roughly 500–1,100 tokens, about 10k in total, which is small enough to ship **verbatim**. None has YAML frontmatter, so Phase 2 has to add it.
- **D6 is confirmed by the docs.** Plugin `settings.json` honors only `agent` and `subagentStatusLine`, and plugins can't ship permission rules. Separately, Bash ask rules match command text and are easy to get around (`git -C . push` slips past `Bash(git push *)`). A plugin `PreToolUse` hook can back them up.
- **D7: nested delegation is VERIFIED in the docs.** A subagent can spawn its own subagents up to 3 levels below the main thread by default. `CLAUDE_CODE_MAX_SUBAGENT_SPAWN_DEPTH` is unset. I didn't test it, because this phase forbids launching agents. Phase 4 has to confirm it in practice.
- **Main risk for D3:** `UserPromptSubmit` also fires on background-subagent reports and on messages from other sessions, not just on what the user types. Without a filter, the escalation hook would fire again on the PM's own results. Two smaller issues: the infra personas overlap heavily, and the PM persona's "every 60 seconds" supervision clause can't run inside a subagent.

## 5. Capability matrix

| # | Question | Status | Evidence |
|---|---|---|---|
| a | Manifest format and component dirs | **VERIFIED** | The manifest is `.claude-plugin/plugin.json` and is optional; only `name` is required. Defaults: `agents/` (`.md`; subfolders become part of the name), `skills/<name>/SKILL.md`, `commands/` (older format; "Prefer `skills/` for new plugins"), `hooks/hooks.json`, `settings.json`. Setting `agents` or `commands` in the manifest **replaces** the default scan; `skills` adds to it; `hooks` merges. A `CLAUDE.md` at the plugin root is **not loaded**. The plugin name can't start with `claude-`/`anthropic-`; `agent-org` is fine. Sources: https://code.claude.com/docs/en/plugins-reference, https://code.claude.com/docs/en/plugins/components. Local: `claude plugin validate --help` |
| b | Plugin `settings.json` and `agent` | **VERIFIED** | "Only two keys take effect from a plugin, `agent` and `subagentStatusLine`; every other key is dropped." Precedence: "plugin defaults are the lowest layer, so a user's own `agent` in `~/.claude/settings.json` overrides yours". When two plugins set it, the one loaded last wins. A root `settings.json` beats the manifest `settings` key. `--agent` overrides the setting. Sources: https://code.claude.com/docs/en/plugins/components#default-settings, https://code.claude.com/docs/en/sub-agents, `claude --help` |
| c | Agent frontmatter fields | **VERIFIED** | Fields plugin agents honor: `name` (required, no `:`), `description` (required), `tools`, `disallowedTools`, `model` (`sonnet/opus/haiku/fable/<id>/inherit`), `effort`, `maxTurns`, `autoCompactWindow`, `skills`, `memory`, `background`, `omitClaudeMd`, `isolation` (`worktree`), `color`, `experimental.cacheTtl`. **Ignored in plugin agents:** `permissionMode`, `hooks`, `mcpServers`, `initialPrompt`. Unknown fields are silently ignored. The agent's full name is `agent-org:<name>`. Sources: https://code.claude.com/docs/en/sub-agents, https://code.claude.com/docs/en/plugins/components#frontmatter-fields-in-plugin-agents |
| d | Can a subagent spawn subagents? | **VERIFIED (docs)**, not tested | "By default, a subagent can spawn subagents of its own, up to three layers below the main conversation." `CLAUDE_CODE_MAX_SUBAGENT_SPAWN_DEPTH=1` turns this off; locally it is **unset**. Leaving `Agent` out of `tools` stops one agent from spawning. With agent teams on, teammates **can't** nest. Source: https://code.claude.com/docs/en/sub-agents. A live test was out of scope for this phase |
| e | Can `UserPromptSubmit` inject context? Plugin hook format? | **VERIFIED** | Yes. Plain stdout on exit 0, or `{"hookSpecificOutput":{"hookEventName":"UserPromptSubmit","additionalContext":"…"}}`, is added as a system reminder. It can block (`decision:"block"` or exit 2) but can't rewrite the prompt. Default timeout is 30s; on timeout the output is thrown away and the prompt goes through anyway. **It also fires on background-subagent reports and on cross-session messages.** `SubagentStart` can inject `additionalContext` into a subagent. Plugin format: `hooks/hooks.json` with a top-level `"hooks"` wrapper, the same shape as settings hooks, using `"${CLAUDE_PLUGIN_ROOT}"` in quotes (or exec form with `args`). Plugin hooks merge with user and project hooks. A plugin's copy of a hook is **not** de-duplicated against an identical user hook. | f | Ask-rule syntax. Can plugins ship permission rules? | **VERIFIED** | `permissions.ask: ["Bash(git push *)"]`; `Bash(x:*)` is the same as `Bash(x *)`. Evaluation order is deny → ask → allow, and the first match wins regardless of specificity. Ask and deny rules apply to any subcommand of a compound command (`&&`, `;`, `|`, `$(…)`). PowerShell uses the same shape, e.g. `PowerShell(Remove-Item *)`; aliases are normalized and matching is case-insensitive. **Rules match command text only:** `Bash(git push *)` doesn't catch `git -C . push`, `/usr/bin/git push`, or `sh -c '…'`. A `PreToolUse` hook can't override deny or ask rules. **Plugins can't ship permission rules**, because plugin settings honor only `agent` and `subagentStatusLine`. | g | Skill frontmatter that blocks auto-invocation | **VERIFIED** | `disable-model-invocation: true` means only the user can invoke it. `user-invocable: false` hides it from `/` so only the model can invoke it. Source: https://code.claude.com/docs/en/skills |

## 6. Conflicts

- **Name collisions:** none. Every component is namespaced (`agent-org:*`). No user agents exist, and the built-in agent types (`general-purpose`, `Explore`, `Plan`, `claude`, `claude-code-guide`, `statusline-setup`) share no IDs with the 14.
- **Overlapping purposes (routing, not names):**
  - `engineering:architecture` and `engineering:system-design` cover the same ground as `solutions-architect`.
  - `engineering:deploy-checklist` overlaps `devops-engineer`.
  - `engineering:code-review` and `engineering:testing-strategy` overlap `quality-assurance-architect`.
  - Every `design:*` skill overlaps `ui-ux-designer`.
  - These are skills, not agents, so nothing double-fires. The model may simply load a skill in the main thread instead of delegating. That's acceptable at Level 0–1.
- **Existing routing or guard systems:** none, so there's nothing to decide between and nothing fires twice.
- **`agent` key in user settings:** absent. D1 wants plain Claude as the main thread, so leaving it unset is correct.
- **Hooks that would double-fire:** none exist today. There are two risks for the future:
  1. Phase 3's "hook wiring" in user `settings.json` could duplicate the plugin's own `hooks/hooks.json`. Plugin and user copies are **not** de-duplicated, so both would run.
  2. The plugin's `UserPromptSubmit` hook fires on non-user prompts too, such as background-agent reports and cross-session messages.
- **Agent teams:** off, so they don't interfere. If someone turns them on, a named PM subagent would become a teammate, and teammates can't nest, which would break the D7 direct-dispatch path.

## 7. What Phase 2 must adapt

1. **Ship no plugin `settings.json`.** *(§5b, D1)* Plain Claude stays the default, and the file's only other key, `subagentStatusLine`, isn't needed. This avoids the plugin quietly changing the main thread.
2. **Wrap each persona body verbatim in new frontmatter.** *(§4: no frontmatter; ≤1.1k tokens each)* Write `plugin/agents/<id>.md` with `name`, `description`, `tools` and `model`. Record the source SHA `89a5424` in a comment or in `plugin.json` `metadata` so drift shows up in diffs. Don't use `permissionMode`, `hooks`, `mcpServers` or `initialPrompt`, because they're ignored in plugin agents.
3. **Fix the D7 dispatch mode: the PM dispatches directly.** *(§5d)* Give `principal-project-manager` the `Agent` tool and the read-only tools, but no `Edit`/`Write`, matching its persona boundary. Give specialists **no** `Agent` tool, so nesting stops at two levels and there are no recursive handoffs. Phase 4 must confirm nesting in a live test. If nesting fails, fall back to "PM returns a plan; main thread dispatches".
4. **Replace the PM's 60-second supervision clause at runtime.** *(§4)* A foreground subagent can't poll on a timer. Add a short runtime note that the PM reports status when each dispatched specialist returns, instead of editing the canonical persona. Alternatively, raise this upstream in agent-personas.
5. **Filter non-user prompts in the escalation hook.** *(§5e)* The `UserPromptSubmit` script must skip prompts that are background-agent reports or cross-session messages. Read the hook payload and check for markers; if no reliable field exists, accept the extra firing and keep the injected text idempotent. Keep it fast (well under the 30s timeout), dependency-free and fail-open, so a hook error never blocks a prompt. Use exec form with `"${CLAUDE_PLUGIN_ROOT}"`.
6. **Hook wiring belongs in the plugin only.** *(§6 double-fire)* The escalation hook lives in `plugin/hooks/hooks.json`. Phase 3 must **not** also add it to user `settings.json`, because the copies aren't de-duplicated. Phase 3 is then limited to `permissions` (ask rules).
7. **Back up ask rules with a plugin `PreToolUse` guard.** *(§5f)* Ask rules miss `git -C . push` and similar forms, and plugins can't ship rules anyway. A `PreToolUse` hook on `Bash|PowerShell` can normalize the command and return `"ask"` for push, deploy, kubectl and cloud-CLI mutations. Keep Phase 3's ask rules as the primary layer; the hook only tightens and can never loosen them.
8. **Give the infra agents disjoint descriptions with tie-breakers.** *(§4 overlap)* Proposed split:
   - **devops:** pipeline and CI files, release, promotion, deployment automation. Owns *IaC wiring into pipelines*.
   - **platform:** shared runtime such as orchestration clusters, service mesh, internal developer platform, paved paths. Owns *reusable IaC modules for shared services*.
   - **cloud:** provider accounts, network, IAM, cost and quotas. Owns *provider resource IaC*.
   - Say who owns secrets: devops for pipeline secret references, cloud for provider secret stores, platform for runtime secret injection.
9. **Use `skills/`, not `commands/`.** *(§5a, §5i)* User-only entry points such as `/agent-org:pm` should be skills with `disable-model-invocation: true`.
10. **Keep the 14 descriptions short.** *(§4)* They load into every session, while the bodies only load on spawn. Aim for one or two lines each that name triggers and exclusions.
11. **Add a stated preference for agents over overlapping skills at Level ≥2.** *(§6 overlap)* The PM's description or the escalation instruction should name the agent-org specialists explicitly, so that `engineering:architecture` and similar skills don't take over escalated work.
12. **Keep this repo public-safe.** *(D8)* Don't commit absolute home paths or synced-bucket IDs. Hooks must read paths from the hook environment.
